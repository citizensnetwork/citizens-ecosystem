| S17 | **DONE 2026-11-01 (PR [#319](https://github.com/citizensnetwork/citizens-ecosystem/pull/319), `e05bef54`): founder chose A, retire it.** `middleware.ts` no longer reads the private profile or signs anyone out (it only refreshes the cookie session); its tests mock a client with only `getUser`, so any profile read or sign-out fails. The columns `force_reauth_at` and `bio_setup_required` and the trigger that stamps `force_reauth_at` are still in the database; a later migration can drop them (no rush, nothing reads them). The finding and evidence follow. *Found 2026-11-01:* Force re-login and the bio-setup gate ran only for cookie sessions, and Connect makes none now.** Plain version: `force_reauth_at` was meant to sign a person out after their role changed, so a stale session could not keep old powers. It never does that for a real person: the browser app keeps its session in localStorage and calls the API with `Authorization: Bearer`; `middleware.ts` skips `/api/*` and only checks cookie sessions; `getRouteAuth` (`src/lib/supabase/route.ts`) checks a bearer token with the auth server but never reads `force_reauth_at`. Nothing sets the cookies any more (only the deleted `auth/callback` route did; Vision and Wear only refresh cookies, none creates them), so the gate can now meet only cookie sessions left over in browsers from the old server-rendered site (retired 2026-06-08). **Why this is not a hole:** a person's role is read from the database on every request, never from the token. RLS `is_admin()` (migration 005, referenced 226 times in migrations) selects from `public.profiles`; `requireAdmin` reads `profiles.role`; the browser reads `profiles.role`; no policy or route reads a role claim, and the `custom_access_token` hook is off and has no function in `supabase/migrations`. So a demoted admin's old token loses its powers at the next statement, whether or not any gate runs. **How it is set:** not by an admin by hand. A BEFORE UPDATE trigger (`trg_profiles_role_change_side_effects`, migration 057) stamps `force_reauth_at = now()` on ANY role change (admin PATCH `/api/admin/users`, `approve_admin_elevation`, the approval RPCs); it also sets `bio_setup_required` on citizen to contributor and clears it on the way back. Migration 057's reason ("so JWT role claims refresh") assumed role claims in the token, which this project never had. **`bio_setup_required`:** only the cookie gate enforces it; `POST /api/contributor/setup` clears it and the onboarding wizard calls that route, but no API or policy requires it, and it only asks for a display name, so it is a nudge, not a security boundary. **Options:** (A, recommended) retire the concept: delete both gates and the per-request profile read from `middleware.ts`, and keep the columns and trigger until a later migration drops them (no behaviour a real person can see changes; it also removes a redirect loop that exists today if the cookie sign-out ever fails). (B) enforce it: in `getRouteAuth` compare the bearer token's `iat` with `force_reauth_at` (one extra `get_my_profile_private` read per authenticated API request, plus a front-end 401 path that signs the browser out; `store.jsx`), so every role change signs that person out on all devices; worth it only if that is wanted as a feature. A real "sign this person out everywhere" lever, if one is ever wanted, is the Supabase Admin API session revoke (not built; I believe the auth server then refuses the old token on `getUser(token)`, unverified). Until you choose, nothing was weakened: the gates stay in `middleware.ts`, redirecting to the app root instead of two pages that do not exist. | P2 | S |
