# S13: who can read who follows whom (audit and proposal, nothing applied)

Written 2026-10-17. Read-only audit of the live database (`list` of policies, grants, functions and views, no person's identity was read; the live tables hold one `follows` row and one `place_follows` row today) and of every reader in the monorepo. **Nothing here changes a policy.** The change is three SQL files plus four small code edits, in a fixed order, and it needs Stephen's yes on each (gate G1, G6).

## The gap, in one paragraph

`public.follows` (a person follows a Contributor) and `public.place_follows` (a person follows a Place) can be read by **anyone holding the public key that every browser carries**: the `SELECT` policy is `true` and `anon` holds `SELECT`. Anyone can list which people follow which ministry. In a Christian community platform that list is sensitive, and it also lets anyone count a ministry's followers directly, which sidesteps the "show a count only from 100" rule (P2-08) that the Map v2 sheet applies. The best time to close it is now: there is one row in each table.

## Three more findings from the same pass

1. **The numbers leak through two public APIs too, not only the table.** `GET /api/v1/contributors/<slug>` returns an exact `counts.followers`, and `GET /api/contributors/search` returns an exact `followers_count` to the public key. So closing the table alone would still leave the exact figure public. Fixing it properly means bucketing at the source (s13a and s13b do): 0 below 100, otherwise rounded down to a step. **This is a visible change** and is Stephen's call (question 2).
2. **Search ranks ministries by how many people follow them** (`sort=auto` and `sort=followers`). That puts the big first and buries the small, against the fourth of our alignment questions ("the small are honoured"). Bucketing makes every ministry under 100 tie, so the tie falls back to name order. That is a side-benefit, not a goal; it is listed so it is a conscious choice.
3. **Fixed in this branch, no yes needed:** every Contributor and Place card and profile page printed `0 followers` (real listings carry no count, so the number is always the default). That is the very low number P2-08 exists to prevent, and it is wrong. They now show the bucket ("100+") or nothing (`window.UI.followerBucket`, `ui.jsx`).

## The proposal, in the order it must be applied

1. **`s13a-follow-count-functions.sql`** (additive, safe alone): `follower_count_public` (bucketed, callable by the public key), `follower_count_exact` (signed-in only), `recipient_follows_me`, and `count_friends` as DEFINER without `anon`. No table or policy is touched, so nothing that works today can break.
2. **`s13b-search-contributors-bucketed.sql`**: `search_contributors` calls `follower_count_public`. This is the visible change in finding 1.
3. **Deploy the code** (four small edits, written after the yes and shipped in the same PR as step 4): `v1/contributors/[slug]` and the dashboard route call the count functions through `rpc`; `conversations` calls `recipient_follows_me`; the broadcasts route runs its two follower lookups as `admin`. Each gets a test that fails if the old table read comes back.
4. **`s13c-follows-tighten.sql`**: the `SELECT` policies become "my own rows" (`follower_id = auth.uid()`, `user_id = auth.uid()`), and `anon` loses every privilege on both tables. A rollback block is in the file.

Applying 4 before 1 to 3 would make public counts read 0 and refuse every Contributor message: the file says so in its header.

### What Contributors lose, on purpose

A Contributor will see **how many** people follow them (Dashboard, exact; public, bucketed) but not **who**. Today the raw rows let any signed-in person list them. Vision's organisation-level insights are aggregate counts and stay as they are. If a ministry should see its followers by name, that would be an opt-in from the follower, a separate feature with its own consent.

## Probe to run at apply time (rollback-only, like the one 181 had)

As `anon`, as the owner of a row, and as a stranger: (a) `select` from both tables returns nothing for `anon`, only the person's own rows for the owner, none of another person's for the stranger; (b) `follower_count_public` returns 0 for 99 rows, `100` for 100 to 249, and the exact steps above that, for `anon` and `authenticated`; (c) `follower_count_exact` and `recipient_follows_me` are refused for `anon`; `recipient_follows_me` is true only for a pair that includes the caller; (d) a signed-in insert and delete of the caller's own row still work; (e) the advisor shows 0 ERROR and no new finding (the new functions are `SECURITY DEFINER` and callable by `authenticated`, which the advisor may report as WARN like the existing ones: list those and justify them in the PR).
